# 좋아요·찜·댓글 지연 점검

작업 브랜치: `max-branch`. 최신 통합 기준: `main`의 `bfb89fe`.
사용자 요청으로 최신 main을 병합하고 지연 개선을 다시 결합한다. 이번 통합은 로컬에 커밋하며 푸시·배포는 진행하지 않는다.

## 최신 main 통합 결과

- 7개 파일 충돌을 해결했다. 최신 main의 Google 지도·번역/사진·국가·프로필·GA4 기능과 데이터 로딩 순서를 보존했다.
- 음식 및 게시글 좋아요는 main의 인증된 RPC(`ieb_set_food_like`, `ieb_set_post_like`)를 그대로 사용한다.
  음식 좋아요 수와 본인 선택 상태, 찜 목록을 즉시 함께 갱신하고 RPC 실패 시 해당 항목만 복구한다.
  음식 좋아요 성공 후 설정 저장은 기존 동작대로 유지하며 대기 중인 설정 변경은 합쳐서 보낸다.
- 댓글은 서버에서 검증한 국가를 계속 저장하며, 저장 응답의 ID/시간/국가로 임시 댓글을 교체한다.
  저장 전에도 회원 국가 배지를 보여준다. 서버의 국가 확인 조회를 제거하거나 클라이언트 국가로 대체하지 않았다.
- main의 DB 음식 목록, 국가별 피드, 기존 좋아요 합계 계산 및 GA4 세션/화면 추적을 유지했다.
  이전 브랜치의 별도 좋아요 테이블 조회·집계 방식은 가져오지 않았다.
- 좋아요·댓글·음식 하트 저장 후의 전체 bootstrap 재조회는 제거했다.
  정상 세션에서 게시글 좋아요의 서버 왕복은 인증+RPC 2회, 댓글은 인증+국가 확인+INSERT 3회다.
  음식 하트는 좋아요 RPC 외에 찜 설정 저장 API도 호출한다. 세션 갱신 여부에 따라 횟수는 달라진다.
- 사진 서명 URL, 회원 정보 등을 다시 받아야 하는 초기 진입·수동 새로고침은 유지한다.

빌드와 자동 검사 29개를 통과했다. 음식/게시글 좋아요 RPC, 국가/프로필/분석, 지도, 번역,
사진/식당 데이터, 공개 진입, 캐러셀, 배포 검사 및 즉시 반영·실패 복구·중복 방지 검사를 포함한다.
기존 테스트의 가짜 응답과 실행 환경도 새 댓글 반환/비동기 상태 알림에 맞춰 갱신했다.

최신 코드의 로컬 브라우저에서 8초 지연 중 게시글 좋아요 2→3, 국가 배지를 포함한 댓글 즉시 추가,
음식 좋아요 수/찜 동시 추가와 실패 후 복구를 확인했다. 실제 DB 연결 없이 격리된 가짜 API로 검증했다.
운영 계정의 영속성 및 DB 실행 계획/cold start 실측은 여전히 미검증이며 DB 스키마/운영 데이터는 변경하지 않았다.
최신 화면은 `docs/verification-engagement.png`다.

## 확인한 원인

- 찜: Store의 상태는 즉시 바뀌지만 app.js가 `Store.flush()` 이후에만 다시 렌더링했다.
- 좋아요·댓글: 저장 API 뒤에 `Store.load()`를 실행하고 그 응답까지 기다렸다.
  bootstrap은 인증 확인, 게시글/댓글/좋아요/프로필/설정 조회와 사진 서명 URL 생성을 포함한다.
  따라서 단일 클릭 결과를 표시하기 위해 불필요한 전체 피드 조회를 기다렸다.
- 음식 상세 재렌더도 최근 음식 기록을 저장한다. 같은 설정까지 매번 쓰거나,
  빠른 조작마다 전체 설정을 직렬로 쌓는 구조라 저장 대기열이 길어질 수 있었다.
- 프레임워크 캐시 재검증은 없는 일반 JS 앱이다. 클라이언트 fetch와 API 응답은
  `no-store`를 사용한다. 개인별 데이터를 공개 캐시로 바꾸는 방식은 사용하지 않았다.

## 운영 사이트에서 측정한 범위

비로그인 브라우저의 좋아요는 로그인 화면으로 이동했다. 운영 테스트 계정과
로컬 `.env.local`이 없어 실제 계정의 쓰기 및 DB 실행 계획/서버 로그는 검증하지 않았다.
운영 데이터 변경 없이 `/api/service?action=bootstrap` 공개 GET만 3회 측정했다.

| 순서 | HTTP | 첫 바이트 | 전체 응답 |
| --- | --- | --- | --- |
| 1 | 200 | 2.168초 | 2.643초 |
| 2 | 200 | 0.761초 | 0.798초 |
| 3 | 200 | 0.929초 | 1.463초 |

응답은 `Cache-Control: no-store`, `X-Vercel-Cache: MISS`였다.
이 3회 측정은 로그인 저장 요청의 성능 비교가 아니며 첫 요청이 cold start였다는 증거도 아니다.
함수/DB 지역과 Vercel의 cold-start 로그를 확인하지 않았으므로 지역 변경은 보류했다.
schema.sql에는 댓글 `(post_id, created_at)` 인덱스, 좋아요 `(post_id,user_id)` 기본 키와
user_id 인덱스, 설정 user_id 기본 키가 있다. 실제 운영 DB 적용 여부는 미검증이며 DB 스키마는 변경하지 않았다.

## 수정 내용

- 찜은 서버를 기다리지 않고 즉시 렌더링한다. 연속 설정 변경은 진행 중 1개와 최신 대기
  스냅샷으로 합치며, 같은 설정은 다시 쓰지 않는다. 최종 저장 실패 시 마지막 확인된 설정으로 복구한다.
- 좋아요는 즉시 숫자/선택 상태를 반영한다. 같은 글의 중복 요청을 막고 실패 시 복구한다.
- 댓글은 임시 항목을 즉시 표시한다. 저장 응답의 실제 ID/시간으로 교체한다.
  실패한 항목은 제거하고, 현재 입력창이 비어 있으면 제출 내용을 복구한다.
- 좋아요·댓글 저장 후 bootstrap을 제거했다. 일반 정상 세션 기준 각각
  브라우저 API 2회→1회, 서버 upstream 9회(사진 서명이 없으면 8회)→2회다.
  실제 요청 수는 세션 갱신·동시 설정 저장 여부에 따라 다르다.
- 진행 중인 댓글 중복 등록, 기존 초안 소실, 오래된 bootstrap 응답에 의한 상태 덮어쓰기를 방지했다.
  다른 화면의 글/프로필/검색 입력창은 늦게 끝난 저장 때문에 재생성하지 않는다.
- bootstrap 동시 호출은 공유하고 좋아요 집계를 단일 순회로 변경했다.
- API `Server-Timing` 헤더에 Auth/DB/Storage HTTP 왕복 시간과 전체 처리 시간을 기록한다.
  이는 순수 SQL 실행 시간이나 함수 시작 이전의 cold start 시간을 직접 측정하지 않는다.
  토큰·사용자 ID·환경변수는 헤더에 포함하지 않는다.
- 변경한 JS의 배포 버전 문자열을 갱신했다. API와 정적 파일을 함께 배포해야 한다.

댓글 저장 결과 반환은 PostgREST의 [return=representation](https://docs.postgrest.org/en/v14/references/api/preferences.html)을 사용해 별도 GET을 피한다.

## 검증

`node tests/engagement-latency.cjs`:
즉시 상태 변경, 중복 요청 방지, 댓글 실제 ID 치환, 실패 복구, 설정 병합/무변경 저장 생략,
bootstrap 중복 방지 및 오래된 응답 무시, 다른 화면 편집 보존을 검사한다.

`node tests/engagement-browser.cjs` → `http://127.0.0.1:8781/#/post/fixture-post`:
실제 서비스 JS와 CSS를 로컬의 가짜 API로 실행한다. 저장 응답에 8초 지연을 넣으며
성공/실패 버튼으로 전환할 수 있다. 실제 Supabase 연결 및 운영 데이터 쓰기는 없다.
브라우저에서 좋아요 즉시 2→3, 댓글 즉시 추가, 실패 시 좋아요/댓글 복구와 입력 내용 복구,
찜 목록 즉시 추가 및 실패 후 제거, 성공 응답 후 다음 댓글 초안 유지를 확인했다.
테스트 서버 요청 기록은 bootstrap 1회와 like 2회/comment 3회/preferences 1회였으며
좋아요·댓글 저장 뒤의 전체 재조회는 없었다. 테스트 서버는 검증 후 종료했다.

기존 인증/API/참여 지표/캐러셀/비동기 사진/지도 통합·계약·로더·수명/원고 검사 및 정적 빌드·배포 검사를 통과했다.
브라우저 결과: `docs/verification-engagement.png`.

## 배포 후 남은 확인

운영 테스트 계정으로 성공/실패·새로고침 후 영속성을 확인하고, Network의 `Server-Timing`과
Vercel 로그를 비교해 Auth, DB HTTP 왕복, 함수 초기 구동을 구분한다.
DB/함수 지역 정렬이나 추가 DB 집계·페이지 분할은 실제 로그/데이터 규모를 확인한 뒤 판단한다.
기존 bootstrap의 조회 상한(글 500, 댓글 5000, 좋아요 10000)은 그대로이므로 대규모 피드의
완전한 집계/페이지 분할은 이번 변경 범위 밖이다.
